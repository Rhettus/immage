# Translating Immage

Immage uses one UTF-8 JSON catalog per language in
[`app/src/locales`](../../src/locales). `en.json` is the reference and final
fallback; `fr.json` is the first translation. The framework accepts BCP 47
language tags, including regional and script variants, so the languages
supported by darktable can be contributed incrementally. Only languages with
a bundled catalog appear in Preferences; untranslated text falls back to English.

## Startup and language selection

Preferences > General > Language defaults to **System default**. At startup,
Immage checks the webview's ordered `navigator.languages` list (falling back to
`navigator.language`). It first tries an exact catalog, then a script-specific
match and parent tags: `fr-CA` can use `fr`, and `zh-TW` can use `zh-Hant`.
If none matches, it uses English. An explicit selection overrides the system.

Settings load before the app is imported, so `t()` can be called at module
level. A changed selection applies on the next launch. **Relaunch** saves the
current photo through the existing app relaunch flow. It does not reload the
webview while edits are pending. The document's `lang` and `dir` follow the
resolved language. Right-to-left catalogs must also be checked for layout,
control alignment and mixed-direction file paths before shipping; setting
`dir` alone does not verify every editing control.

## Adding a language

1. Create a canonical BCP 47 filename, for example `de.json`, `pt-BR.json`,
   `zh-Hant.json` or `sr-Latn.json`. Copy the English keys you can translate;
   partial catalogs are allowed. All interface translations for that language
   stay in this file; user guides are separate.
2. Translate values, preserving `{placeholder}` names. The build discovers
   catalogs automatically. No import or registration change is needed; the
   language selector uses the language's own name from `Intl.DisplayNames`.
3. Run `node --test verify/locales.test.mjs verify/menus.test.mjs` and
   `npm --prefix app run build`. Checks reject unknown keys, invalid filenames,
   non-string or empty values, and changed placeholder names.
4. Check translated screens on a native app, including longer labels, font
   coverage and text direction. Do not list an untranslated language merely
   because darktable supports it. Native OS menu roles and bundled Immporter
   text have their own localization behavior.

## In code

```ts
import { t, formatNumber, formatDate } from "./i18n";
t("menu.export")
t("import.done", { count: formatNumber(1234) })
t("photos", { n: 3 })
formatDate(new Date(), { dateStyle: "medium" })
```

Keys are semantic (`menu.export`), independent of English wording. Use complete
messages with named placeholders rather than concatenating translated fragments.
For plural messages, `n` is a raw number used by `Intl.PluralRules`. Define the
categories that language requires as `photos_zero`, `photos_one`, `photos_two`,
`photos_few`, `photos_many`, and/or `photos_other`. English normally needs
`_one` and `_other`; other languages may add categories absent from English.
Each category must preserve the English message's placeholders. Interpolation
is plain text; render it through React, never as HTML.

For each message, lookup checks the selected catalog, available parent catalogs,
then English. Each fallback language uses its own plural rules, so French zero
correctly falls back to English `0 photos`. Within a catalog it tries the
selected plural form, the unsuffixed message, then `_other`. An unknown key is
shown literally so missing reference entries are visible during development.
`formatNumber` and `formatDate` use the chosen UI language. Use them only for
display; numeric input values, saved settings, protocol numbers and filenames
must keep their existing formats. Existing `toLocale*()` calls use the system
locale until the relevant screen is converted.

## Converting a screen

Replace user-facing text with `t("area.name")` and add keys to `en.json` and
`fr.json`. The menus and Preferences have the initial conversion; shared panel,
module and plugin descriptions, themes, and the remaining screens still contain
English. Keep names of unconverted panels in English inside translated help so
they match the screen. The framework is app-wide; catalogs do not automatically
translate strings that have not been converted.

A `PrefRow` takes translated `label` text and its stable English name as `id`
(`data-pref-label`), preserving GUI test selectors. Do not decide behavior from
translated text; keep flags or stable IDs for lookups and status styles.
License and copyright notices remain in their original wording.
